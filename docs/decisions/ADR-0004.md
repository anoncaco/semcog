# ADR-0004: §10.2 대표 예시를 파싱할 수 있도록 §7.3 문형 표 확장

- **상태:** 확정 (Accepted)
- **일자:** 2026-10-20
- **관련:** `summary_arch.md` §2 C14, §7.3, §7.5.1, §8.10, §10.2, §16 Phase 3·Phase 6, §19 #13·#15
- **기반:** 아키텍처 검토 M9

## 배경

1차 목표를 "Phase 0~5 + Phase 6 대표 예시(§10.2) 선행 검증"으로 확정했으므로, **§10.2 예시가 실제로 파싱되는지**가 도달 가능성의 관건이 되었다.

§7.3의 한국어 문형 표(9행)와 §10.2의 두 입력을 문형 단위로 대조했다.

### 입력 1 — "동물 A의 귀가 뾰족하다"

- §7.3 행 5 `"A의 B"` → `(.+?)의 (.+)` 매칭: subject=`동물 A`, attribute=`귀가 뾰족하다`
- §7.3 표 하단 "속성 표현 노이즈 제거" 규칙: `귀가 뾰족하다` → canonical_label `뾰족한 귀`
- **→ 매칭됨.** 단, 속성 정규화가 **선언된 규칙으로 존재해야** 구현된다.

### 입력 2 — "개도 뾰족한 귀를 가질 수 있다"

| 후보 행 | 매칭 여부 | 사유 |
|---|---|---|
| 행 4 `A는 B일 수 있다` | ✗ | 조사 `도`·어미 `가질 수 있다` 불일치 |
| 행 5 `A는 B를 가진다` / `A의 B` | ✗ | 조사 불일치 / `의` 없음 |
| 행 7 `A도 B이다` | ✗ | `도`는 있으나 어미가 `이다`가 아님 |
| 행 1~3, 6, 8, 9 | ✗ | — |

**→ 어떤 행에도 매칭되지 않아 `unparsed`가 된다.**

§7.3은 "v1이 지원하는 것은 위 표뿐이다. 이 표를 넘는 문형은 억지로 추출하지 않는다"고 규정한다. 따라서 현행 규칙으로는:

- Phase 3 게이트 "속성 노드가 공유되어 §10.2 예시가 재현 가능" → **불가능**
- Phase 6 게이트 "§10.2 대표 예시가 end-to-end로 재현됨" → **불가능**

문서 자신의 대표 사례가 문서 자신의 규칙으로는 실행되지 않는 상태였다.

## 검토한 대안

| 대안 | 평가 | 문형 행 수 | §19 #15 72문장 |
|---|---|---|---|
| (a) §10.2 예시 문장을 지원 문형으로 재작성 | 규칙 변경 없이 게이트가 열린다. 단 §10.2 본문·Phase 3/6 게이트 문구를 함께 고쳐야 한다. **대표 사례의 원문이 바뀌는 부작용** | 9 유지 | 유지 |
| (b) §7.3 표에 새 행 추가 | 가능하나 문형 행이 10이 되고 개발 세트가 27→30으로 늘어난다 | **10** | **위반** |
| **(c) 기존 행에 표면형 추가 (행 유지)** | 규칙 확장은 최소로 하고 대표 예시 원문도 유지된다 | **9 유지** | **유지** |
| (d) 예시 실행을 Phase 6 게이트에서 제외 | 1차 목표의 마지막 게이트가 사라진다. **기각** | — | — |

## 결정

**기존 행에 표면형을 추가한다(C).** §7.3 표를 다음과 같이 확장한다.

| 행 | 기존 표면형 | 추가 표면형 |
|---|---|---|
| `has_property` / `possible` | `A는 B일 수 있다`, `A는 B일 가능성이 있다` | **`A도 B를 가질 수 있다`, `A가 B를 가질 수 있다`** |
| `has_property` / `typical` | `A는 B를 가진다`, `A의 B` | **`A의 B가 C하다`** |

추가 규칙:

- **주체 조사 허용:** `는`, `은`, `도`, `가` 모두 허용. `도`는 주어를 바꾸지 않는다("개도 …" → subject=`개`).
- **가능성 동사(`…를 가질 수 있다`)는 계정 용언(`…일 수 있다`)과 같은 `possible` 양태.** 별도 술어를 만들지 않는다(P9).
- **형용사 서술(`A의 B가 C하다`)은 `has_property`/`typical`.** attribute 원형은 "B가 C하다"이고 정규화 결과는 `configs/attributes.yaml` 규칙을 따른다.
- **문형 행은 9개로 고정.** 새 행 추가는 §7.5.1 개발자 경로의 구조 변경이다.

**§10.2 원문은 대표 예시로 유지한다.**

**속성 정규화의 config화:** "귀가 뾰족하다" → "뾰족한 귀" 변환을 §7.3의 설명 문장에서 **`configs/attributes.yaml`에 선언된 규칙**으로 옮긴다. §8.10 `resolution_method`는 `literal_normalized_match` → `alias_table` → `unresolved` 순으로 시도하고, 적용된 규칙을 기록한다.

**§10.2에 실행 전제와 기대 결과 단언을 추가한다.** Phase 6 통과 판정의 기준이 문서에 명시되어야 하므로:

- 실행 전제 5개 (두 문장 파싱 / 속성 노드 공유 / 후보 분류 "고양이" 존재 / distinctiveness `not_distinctive` / V의 counters 2-경로)
- 기대 결과 단언 (H1 `unresolved` / 어떤 가설도 `supported` 아님 / 고양이가 사실로 승격되지 않음 / `counter_evidence` 포함 / `open_questions` 추가 / `unknown`과 `not_distinctive` 구분)
- **여러 가설이 생성되어도 무방** — H1의 상태와 반증 연결만 단언한다.

## 결과

- Phase 3·Phase 6 게이트가 도달 가능해진다.
- §19 #15의 72문장(27/15/10/20) 구성이 **그대로 유지**된다(문형 행 수 불변).
- §19 #13이 "9개 행 고정"으로 해소된다.
- 대표 예시 원문이 유지되어 §10.2의 참조 안정성이 보존된다.
- **의존성 규칙이 config로 이동**되어 META가 §7.9 허용 목록 안에서 수정할 수 있게 된다(§7.3의 "코드 하드코딩 금지" 원칙과 일치).

## 잔여 위험

- 표면형 추가만으로 실제 구현이 모든 변형을 처리한다는 보장은 없다. **Phase 3에서 72문장 라벨 세트로 precision/recall을 측정**해야 하며, 미달하면 §7.5.1 경로로 규칙을 더 보강한다.
- "A의 B가 C하다"의 주어 경계는 "A의"에서 자른다. "모든 A의 B가 C하다"처럼 수량사가 앞에 오면 주어가 잘못 잡힐 수 있다. **대립 세트(15문장)에서 반드시 검증**한다.
