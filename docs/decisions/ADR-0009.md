# ADR-0009: Phase 판정 3상태 (통과 / 실패 / 보류)

- **상태:** 확정 (Accepted)
- **일자:** 2026-10-20
- **관련:** `summary_arch.md` §4 P13, §15.7, §16, §18.4
- **기반:** 아키텍처 검토 §1.1

## 배경

§16은 "각 단계는 코드·테스트·실측 results.json·REPORT.md가 모두 끝나야 다음으로 넘어간다"를 규정했지만, **Phase의 판정 상태가 2개(통과/실패)뿐**이었다.

문서 안에 이미 3상태적 판단의 근거가 세 곳 있었다.

- §15.7: "측정법이 정의되지 않으면 **'측정 불가'로 기록한다**"
- §4 P13: "평가 실패는 보통 설계 결함이 아니다. 입력 인식 오류·검색 실패·규칙 버그·근거 부족·데이터 부족 중 무엇인지 먼저 분류한다"
- §18.4: "오류당 최대 3회 수정 시도. 그 이상이면 로그를 남기고 멈춘다"

문서 §§15.7과 P13이 사실상 "아직 판단할 수 없는 상태"를 전제하고 있었는데, 판정 체계에는 그 상태가 없었다.

## 결정

| 판정 | 의미 | 다음 행동 |
|---|---|---|
| **통과** | 사전에 정의한 통과 기준을 모두 충족 | 다음 Phase 착수 가능 |
| **실패** | 기준을 충족하지 못함 | §5.3 진단 순서로 원인 분류 → §18.4 수정 시도(최대 3회) |
| **보류** | 환경·데이터 부족·측정 불가로 **판정 자체가 불가능** | 기준을 임의로 낮추지 않는다. 해소 조건을 명시하고 남겨 둔다 |

**규칙**

- **보류를 통과로 취급하지 않는다.** 보류는 다음 Phase 착수를 막는다.
- **보류 ≠ 정지.** §18.4의 "3회 소진 후 정지"는 수정 시도가 실패한 경우다. 보류는 원인이 환경·데이터에 있어 수정으로 해결되지 않으며, 해소 조건을 명시한다.
- **실패 ≠ 설계 결함.** P13에 따라 원인 분류가 먼저다.
- **판정 근거는 항상 기록한다.** 통과/실패/보류 어느 것이든 `experiments/stageN_*/results.json`에 판정·근거·미해결 항목을 남긴다.

**Phase 4종 세트의 테스트 범위를 명시한다.**

1. `<주제>.py` — 실험 본체. 실행하면 `results.json`을 스스로 쓴다.
2. `test_<주제>.py` — pytest 단위 테스트 (정상·오류·경계 조건).
3. `results.json` — 실제 실행 산출물(명령·시드·수치·소요시간·**판정 상태** 포함).
4. `REPORT.md` — 사람이 읽는 요약(결과·실패 원인·통과 여부·**미해결 사항**).

**통합 테스트**는 이전 Phase와의 연결 확인, **회귀 테스트**(`tests/regression/`)는 기준선 유지 확인이며, §7.5.1 개발자 경로의 게이트 2가 실행한다.

## 결과

- "측정 불가"가 정식 판정 상태가 되어, §15.7과 §16이 정합한다.
- 보류 상태는 다음 Phase를 막되, 해소 조건이 명시되므로 막다른 길이 아니다.
- Phase마다 무엇이 통과 조건인지, 결과에 무엇을 적어야 하는지가 §16에 고정된다.
