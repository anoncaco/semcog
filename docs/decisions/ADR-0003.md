# ADR-0003: 근거 계보(`lineage`)와 실패 지점(`failed_stage`) — 두 축 분리

- **상태:** 확정 (Accepted)
- **일자:** 2026-10-20
- **관련:** `summary_arch.md` §2 C13, §8.3, §8.4, §8.5, §8.11, §8.12, §11.1, §7.7
- **기반:** 아키텍처 검토 A(수정 채택) + M4

## 배경

두 가지 문제가 있었다. 둘은 겉보기에 비슷하지만 **서로 다른 축**이다.

### 문제 1 — 근거 독립성이 표현되지 않는다

§8.4 `Evidence`에는 출처(`source_kind`)는 있지만 **파생 계보가 없다.** "같은 원본을 복사한 자료 10건"과 "서로 독립한 출처 10건"이 구별되지 않는다.

이 구별이 없으면 **세 곳이 동시에 부풀어진다.**

| 위치 | 영향 |
|---|---|
| §11.1 `importance`의 `evidence_weight` | 근거 3개 포화 기준이 복사본 3개로 채워진다 |
| §8.3 `confidence_components.support_count` | 지지 근거 수가 실제보다 크게 잡힌다 |
| §7.7 `induction.common_relation`의 최소 사례 수 | "여러 독립 사례"가 여러 복사본이 될 수 있다 |

§10.4는 이미 "최소 사례 수, **독립 출처**, 예외 기록"을 요구하고 §7.7 연산 표도 "여러 **독립** 사례"를 말하지만, **이를 측정할 필드가 없었다.**

### 문제 2 — 실패 지점이 기록되지 않는다

§8.11 `FailureCase`의 `diagnosis_category`는 근본 원인 7종(`input_error` | `retrieval_error` | `rule_error` | `evidence_missing` | `representation_limit` | `policy_error` | `data_missing`)이고, §8.11은 **"동일한 7종을 쓴다. 임의 확장하지 않는다"**고 명시한다.

한편 §5.3의 진단 순서는 "입력 추출 오류 → 기억 검색 오류 → 추론 규칙 오류 → 근거 부족 → 표현 체계 한계 → 정책 오류 → 데이터 부족"으로 7단계다. 즉 **7종은 근본 원인 축이면서 동시에 파이프라인 단계 축**처럼 쓰이고 있다.

외부 검토는 8종(`encoding_error`, `parse_error`, `inference_error`, `verification_error` 등)을 제안했다. 이는 §8.11의 명시 규칙을 위반하며, 근본 원인과 발생 단계를 혼동한다.

## 검토한 대안

| 대안 | 평가 |
|---|---|
| (a) `diagnosis_category`를 8종으로 확장 | §8.11 "임의 확장하지 않는다" 위반. META의 원인 분류 의미가 흐려진다. **기각** |
| (b) `diagnosis_category`를 단계 기준으로 재정의 | 7종의 근본 원인 의미(META의 §7.9 분류와 동일)가 사라진다. **기각** |
| **(c) 7종 유지 + 별도 축 2개 추가** | **채택** |

## 결정

### 축 1 — `Evidence.lineage` (신규, §8.4)

```json
"lineage": {
  "source_group_id": "srcgrp_...",
  "derivation_kind": "direct | copy | paraphrase | derived",
  "derived_from_evidence_ids": []
}
```

- `source_group_id`: 독립 출처 그룹 ID. **같은 원본에서 파생된 근거는 같은 ID.**
- v1 판정 규칙: `provenance.source_id`가 같으면 같은 그룹, 다르면 다른 그룹.
- **독립 개수 = `source_group_id`의 서로 다른 값 개수.**

### 축 2 — `FailureCase.failed_stage` + `diagnosis_status` (신규, §8.11)

```json
"failed_stage": "adapter | encoder | parser | registry | retriever | reasoner | verifier | policy | store | runtime",
"diagnosis_status": "suspected | confirmed"
```

- `failed_stage` = **관측 사실**(어디서 빠졌는가). `diagnosis_category` = **판단**(왜 그런가).
- 한 실패가 두 축에서 다른 값을 가질 수 있다. 예: `failed_stage=parser`, `diagnosis_category=rule_error`.
- `diagnosis_status`는 원인이 확정되었는지를 구분한다. META가 `suspected`를 `confirmed`로 올릴 수 있다.

### 적용 — 독립 근거 기준 3곳 통일

**§8.3 `confidence_components`, §11.1 `evidence_weight`, §8.12 `independent_case_count`가 모두 `source_group_id` 기준을 사용한다.** 셋이 서로 어긋나면 안 되며, 테스트로 검사한다. 원시 개수도 함께 기록해 어느 값을 썼는지 구분 가능하게 한다.

### 추가 — `InferenceTrace.scope` (신규, §8.5)

외부 검토가 "distinctiveness의 `distinctive`는 명시된 검사 범위에서만 성립한다"는 정의를 제안했다. 이는 §7.7의 기존 정의(`distinctive`/`not_distinctive`/`unknown`)를 **변경**하는 것이 아니라 **범위를 명시**하는 것이므로 스키마 확장으로 처리한다.

- `distinctive`는 `scope`가 없으면 **허용되지 않는다.** `not_distinctive`·`unknown`은 `scope` 없이도 유효하다.
- v1 검사 범위 = 현재 SymbolicStore에 존재하는 주어 전체. **`node_type`에 의존하지 않는다**(§8.10의 `node_type` 판정이 불확실한 v1 환경에서 §10.2 재현을 보장하기 위함).

## 결과

- §8.11의 "7종 고정" 규칙이 지켜진다.
- 근거 독립성이 측정 가능해진다. `importance`·`confidence`·귀납 최소 사례 수가 서로 어긋나지 않는다.
- 실패 기록에서 "어디서"와 "왜"가 분리되어, 오류 처리·재시도 설계와 원인 분석이 각각 가능해진다.
- `distinctive`가 전역적 진술로 오해될 여지가 사라진다.

## 잔여 위험

- `source_group_id`의 v1 판정(`source_id` 동일 → 같은 그룹)은 보수적이지 않다. 같은 출처의 서로 다른 관측이 다른 그룹으로 잡힐 수 있다. §19 #24에 "수동 병합 절차"를 미정으로 남긴다.
