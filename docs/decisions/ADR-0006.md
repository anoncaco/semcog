# ADR-0006: 이벤트 스토어 책임 분담 (Phase 4 ↔ Phase 5)

- **상태:** 확정 (Accepted)
- **일자:** 2026-10-20
- **관련:** `summary_arch.md` §7.5, §7.6, §16 Phase 4·Phase 5, §17
- **기반:** 아키텍처 검토 "문제 1"

## 배경

문서 안에 이벤트 스토어 구현이 **두 Phase에 걸쳐 중복으로 지정**되어 있었다.

| 위치 | 지정 내용 |
|---|---|
| §7.6 저장 계층 | "Event Store \| 상태 변화·추론·메타 변경 이력 \| SQLite" |
| §7.5 이벤트 기반 상태 갱신 | "최초 구현은 SQLite 이벤트 로그면 충분한다. 이벤트로 어떤 입력·규칙이 상태 변화를 일으켰는지 재현·디버그할 수 있어야 한다" |
| §16 Phase 4 산출물 | "…**이벤트 스토어**, 심볼릭 store API" |
| §16 Phase 5 산출물 | "…**이벤트 로그**, 영속 저장·복원, 세션 관리" |

같은 기능을 두 Phase가 각각 만든다. 그대로 진행하면 (1) 구현이 두 번 되거나 (2) 어느 Phase가 무엇을 만들었는지 모호해진다. 어느 쪽이든 §16의 "단계 건너뛰기 금지"와 충돌한다.

특히 Phase 4는 **기억 계층**이고 Phase 5는 **상태 관리 계층**이다. 두 계층의 이벤트는 성격이 다르다. 기억 이벤트는 "무엇이 저장·검색되었나"를, 상태 이벤트는 "무엇이 판정되었나"를 기록한다.

## 검토한 대안

| 대안 | 평가 |
|---|---|
| (a) Phase 4가 이벤트 스토어를 완전히 만든다 (Phase 5는 사용만) | Phase 5의 상태 이벤트 스키마·원자성 요구가 Phase 4에서 미리 설계되어야 한다. **책임이 앞당겨진다.** 기각 |
| (b) Phase 5가 이벤트 스토어를 완전히 만든다 | Phase 4가 기억 이벤트를 기록하지 못한다. §8.7 `RetrievalTrace`·P11(저장≠검색≠활용) 검증이 Phase 4 게이트에서 불가능. **기각** |
| **(c) Phase 4 = 인프라 + 기억 이벤트 / Phase 5 = 상태 이벤트 + 스냅샷 + replay** | **채택** |

## 결정

**이벤트 스토어를 2단계로 나눈다.**

### Phase 4 — 이벤트 스토어 **인프라** + 기억/검색 이벤트

- SQLite 이벤트 테이블, 인덱스, 멱등 쓰기 API (§9 `write_event`)
> **정정 (v1.4.0, ADR-0011):** 이 문서의 "이벤트 **스키마 12필드**"는 오기다. 정본(`summary_arch.md` §7.5 · `configs/structure_registry.yaml` `event_schema_fields` · `docs/DATA_MODEL.md` §3.11 DDL 3자 일치)은 **9필드**다 — `event_id`, `event_type`, `session_id`, `step`, `actor`, `subject_ids`, `reason`, `payload`, `created_at`. **9개가 최소이며, `event_type`별 추가 필드는 `payload`에 넣는다**(컬럼을 늘리지 않는다). 아래 본문의 "12필드" 표현을 이 정정으로 대체한다. 결정 자체(Phase 4/5 책임 분담)는 변경되지 않는다.

- 이벤트 **스키마 9필드(최소)**의 **기반 구조**만 정의 (`event_id`, `event_type`, `session_id`, `step`, `actor`, `subject_ids`, `reason`, `payload`, `created_at`)
- 기록 대상: `ContextAdded`, `RelationExtracted`, `RetrievalPerformed`, `SearchResultUsed`, `SearchResultIgnored`, `EncoderFailed`, `ParseFailed`, `RetrievalFailed` 등 **기억 계층 이벤트**
- **Phase 4 게이트에서는 이벤트 인프라 + 기억 이벤트가 동작해야 한다.**

### Phase 5 — STATE 전이 이벤트 + 스냅샷 + 복원·replay

- `HypothesisCreated`, `HypothesisWeakened`, `HypothesisRejected`, `ContradictionDetected`, `EvidenceLinked`, `ObservationRequested`, `TransitionRejected`, `StructureChangeProposed`, `StructureVersionActivated`, `StateSaved`, `SessionStarted`, `SessionResumed`, `SessionEnded`, `StepTerminated` 등 **상태 전이 이벤트**
- **상태 스냅샷** 저장/복원 (`data/sqlite/state/<session_id>/<step>.json`)
- **이벤트 replay** — 스냅샷 이후의 이벤트를 재적용해 상태 재구성
- **원자성** — 상태 변경과 이벤트 기록이 **단일 트랜잭션**으로 처리된다. 실패 시 부분 반영된 상태를 "완료"로 취급하지 않는다.
- **Phase 5 게이트에서 이벤트 스토어가 완성**된다.

### Phase 8 — 인지 루프의 스텝 이벤트 연결

- §10.1의 7스텝이 각 스텝 시작·종료 이벤트를 남긴다. 이는 Phase 8의 책임이며, Phase 5는 **기반만** 제공한다.

## 결과

- Phase 4와 Phase 5의 산출물이 겹치지 않는다.
- **원자성 요구가 Phase 5에 정확히 귀속**된다. Phase 4는 단일 엔티티(기억) 저장에 대한 멱등성만 책임진다.
- §8.7 `RetrievalTrace`와 P11 검증이 Phase 4 게이트에서 수행 가능하다.
- Phase 6~9는 완성된 이벤트 기반 위에 올라간다.

## 잔여 위험

- Phase 4가 만든 이벤트 테이블 스키마를 Phase 5가 확장해야 할 수 있다. **Phase 4에서 Phase 5가 필요로 할 필드를 미리 포함**한다(`event_type` 인덱스, `payload` JSON 확장성, `session_id`/`step` 인덱스).
