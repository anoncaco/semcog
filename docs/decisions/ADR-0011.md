# ADR-0011: 문서 간 모순 정합 (전이 사유 우선순위 · 대응 술어 표현 · 정정 8건)

- **상태:** 확정 (Accepted)
- **일자:** 2026-10-20
- **관련:** `summary_arch.md` §7.3, §7.5, §7.6, §8.1, §8.2, §16, §17, §19 #25, §21
- **기반:** 3자(메인·Beam·GLM) 교차 감사 — 판별 프로브 + 전수 대조
- **규범 버전:** `summary_arch.md` v1.4.0-merged

## 배경

Phase 0 착수 전, 규범 문서(`summary_arch.md`)와 파생 문서·config 사이에 **모순이 8건 + 신규 6건** 확인됐다. Phase 0 이후 발견되면 구현 도중 혼란을 만드는 유형이므로, 착수 전에 정리한다.

**원칙 3종를 먼저 구분했다** (사용자 지정).

1. **명백한 모순** — 관련 문서와 설정을 일치시킨다.
2. **의도가 불명확한 부분** — 설계 의도를 확인한 후 수정한다.
3. **아직 결정하지 않은 설계 사항** — 임의로 결정하지 않고 미결 사항으로 남긴다.

**중요한 구분: 모순을 제거하는 것과 새로운 설계 결정을 내리는 것은 다르다.** 아래 ①②③은 사용자에게 확인받아 확정했다.

## 결정

### ① 전이 사유 규칙 — 전역 규칙 우선 (A3)

**확정: 전역 규칙이 우선한다. 개별 전이 규칙은 전역을 완화하지 못한다. 강화만 할 수 있다.**

| 위치 | 내용 |
|---|---|
| `summary_arch.md` §7.5 | "각 전이는 `apply_transition(state, transition, reason)`을 통과하며 `reason`이 비어 있으면 거부한다" |
| `summary_arch.md` §9 | `def apply_transition(state, transition, reason) -> State` — `reason`은 **선택 인수가 아니다** |
| `summary_arch.md` §16 Phase 5 게이트 | "모든 상태 변경에 사유·출처 남음" |
| `summary_arch.md` §10.1 6단계 | "UPDATE apply_transition (사유·출처·이벤트 남기고 상태 갱신)" |
| `configs/structure_registry.yaml` | `global_transition_rules.require_reason: true` + 헤더 주석 "모든 전이는 reason이 비어 있으면 거부된다" |

**문제:** 개별 항목 12개의 `requires_reason: false`가 전역 규칙을 상쇄하고 있었다. `requires_reason: true` 2개는 전역과 중복이었다.

**해결:**
- `requires_reason` 필드 **14개 전부 제거.** 전역 `require_reason: true`가 단일 기준이 된다.
- 개별 규칙이 표현하는 것을 **사유 존재 여부가 아니라 내용의 종류**로 바꾼다. → **`reason_kinds`** 필드 신설.
  - 값: `existing_evidence_retracted` (기존 근거 철회) / `new_evidence_added` (신규 근거 발생)
  - §7.5:598의 괄호 "(기존 근거철회·신규 근거 발생)"를 그대로 enum화한 것이므로 **새 설계가 아니라 서술된 요구의 코드화**다.
- §7.5의 **"재검토 시에만"**은 별도 boolean으로 두지 않고 `reason_kinds` 충족으로 판정한다 (필드 1개로 충분).
- 판정 순서: (1) `reason` 비면 거부 → (2) `reason_kinds` 있으면 그중 하나 명시해야 함 → (3) 그 외 통과.

**인용 근거:** §7.5:599는 예외 절 없는 보편 규정이고, §7.5:598의 괄호는 사유의 **존재** 조건이 아니라 **내용** 조건이다. 두 절은 상호 보완적이며, **전역 우선이 두 절을 동시에 만족하는 유일한 해석**이다. 개별 우선 해석은 규범 3곳(:599·Phase 5 게이트·§10.1)을 완화해야 하므로 ADR 근거가 필요하다.

> **검증 노트:** 판별 프로브에서 어떤 모델은 "개별 우선"으로 판정했다. 개별 `requires_reason: false` 12개가 **ADR 근거도 규범 문장도 없는 무배경 데이터**이고, 데이터의 존재가 데이터의 올바름을 증명하지는 않는다. 2기독(Beam·GLM)이 전역 우선으로 독립 재확인했다.

### ② 대응 술어 표현 (A1)

**확정: `predicate`는 술어 사전 11종의 값만 넣는다. `not_is_a` 같은 대응 술어명은 절대 넣지 않는다. 부정 여부는 `polarity=negative`로만 표현한다.**

- 정본 3자(`summary_arch.md` §7.3:515·§8.2 / `docs/DATA_MODEL.md` §3.2 / `configs/relations.yaml`)가 이미 이 의미로 일치했다.
- **문제는 3개 표의 술어 열이 `(대응 술어)`라는 플레이스홀더를 쓰고 있었다.** 라벨러가 JSONL의 `predicate`에 채울 값이 없어 라벨 스키마가 파탄났다.
- 특히 `is_a_also`(극성 `positive`) 행에 `(대응 술어)`가 붙은 것은 논리적으로 불가능했다(대응 술어 = 부정형).
- `configs/relations.yaml`의 `counterparts:` 맵과 패턴의 `counterpart:` 필드는 **표현용 별칭**임을 주석으로 명시했다.

**수정:** `summary_arch.md` §7.3 표 · `docs/EXPERIMENT_PROTOCOL.md` §2.4 · `tests/fixtures/parsing/README.md` 3개 표의 술어 열을 `is_a`로 통일.

### ③ 이벤트 스키마 필드 수 (A2)

**확정: 9필드가 최소 정본이다. `event_type`별 추가 필드는 `payload`에 넣는다.**

사용자 지적("12개라고 기록을 무조건 9개로 바꾸지 말고, 나머지 세 필드의 정의가 다른 문서에 있는지 먼저 확인")에 따라 **먼저 확인했다**.

| 출처 | 필드 수 | 내용 |
|---|---|---|
| `summary_arch.md` §7.5 | **9** | "이벤트 스키마 (최소 9필드)" |
| `configs/structure_registry.yaml` `event_schema_fields` | **9** | 정본과 이름까지 동일 |
| `docs/DATA_MODEL.md` §3.11 DDL | **9** | 컬럼 9개, 동일 |
| `docs/decisions/ADR-0006.md` | "12" | **12라면서 바로 뒤에 9개만 열거** — 문장 자체가 자기 모순 |
| `docs/IMPLEMENTATION_PLAN.md` T5.5 | "12" | 목록 없음 |

추가 필드 후보(`correlation_id`·`causation_id`·`parent_event_id`·`event_hash`·`trace_id`·`phase`·`actor_role`) 전수 검색 결과 **이벤트 필드로 정의된 것이 없음**(`trace_id`는 `inference_traces` 테이블, `inference_trace_id`는 `hypotheses` 컬럼). **"12"는 문서화된 필드가 없는 수치**였다.

**결정:** 정본 3자 일치가 9이므로 9가 정본. `summary_arch.md` §7.5에 **"추가 필드는 `payload`"** 원칙을 명문화하고, ADR-0006에는 **정정 주석**으로 남겼다(accepted ADR 무기명 덮어쓰기 방지).

### ④ 전이표 나머지 불일치 3건 (B1·B2·B3)

| 지점 | 표 | config | 판정 | 조치 |
|---|---|---|---|---|
| `supported → rejected` | `✅` | `allowed: false` | **표 셀이 오류.** 불릿(:597 "직행 금지")·config·테스트 3곳이 금지 | 표 셀 → `—` |
| `rejected → supported` | `(사유 필수)` | `allowed: false` | **config가 과다 금지.** 표·config 헤더(:18)·테스트("(사유 없이)"만 불법)가 허용 전제 | `allowed: true` + `reason_kinds` |
| `rejected → unresolved` | `(사유 필수)` | 조건 표현 없음 | 허용·사유는 일치, **전제 표현 누락** | `reason_kinds` 추가 |

§7.5:598이 "rejected에서 **되돌아오는 전이는** 사유 필수"라고 명시하므로 `rejected` 행 3개 셀을 모두 `(사유 필수)`로 통일했다.

### ⑤ 라벨 세트 — 파일과 세트의 축 분리 (B6)

**문제:** `parsing_dev`가 **27(세트)** 과 **52(파일)** 를 동시에 가리켰다.

- `summary_arch.md` §7.3 표: "개발 세트(`parsing_dev`) 27" / "대립 세트(`parsing_adv`) 15" / "비지원 세트(`parsing_oos`) 10"
- `summary_arch.md` §15.1.1·`docs/EXPERIMENT_PROTOCOL.md` §2.1·`data/data_manifest.yaml`·`tests/fixtures/parsing/README.md`: `parsing_dev` = **52** (27+15+10), 파일 2개

게다가 라벨 JSONL 스키마에 27/15/10을 구분할 필드가 없었다(`split`은 `dev`/`holdout`만).

**스키마 변경 없이 구분하는 3가지 우회안은 모두 배제했다:**
1. `split` 값 확장 — `split`은 **분할 파티션** 개념이고 27/15/10은 같은 분할 안의 **용도 구분**이다. `results.json`·`data_manifest.yaml`·ADR-0007가 이미 등록한 분할 도구를 semantic 변경하게 된다.
2. `pattern_id`/`parse_status`로 역식별 — `is_a_all`·`is_a_some`은 9문형 구성분이라 대립 세트에도 있을 수 있고, `unparsable` 항목은 개발 커버리지와 비지원 세트 양쪽에 존재할 수 있다. **구별 불가.**
3. `id` 접두사 관례 — 수동 라벨링(초안→검수)이라 재배치될 수 있고 검증 불가.

**결정: 신규 `subset` 필드 추가** (값: `base`/`adversarial`/`out_of_scope`/`holdout`).
- §7.3의 세트 id `parsing_dev`/`parsing_adv`/`parsing_oos`를 `base`/`adversarial`/`out_of_scope`로 **rename**한다. 파일 dataset ID(`parsing_dev`/`parsing_holdout`)는 5곳+ 참조이므로 **보존**한다. → **ID와 세트 값이 같은 문자열을 공유하지 않는다.**
- `split`(파일 분할)과 `subset`(문장 역할)은 **다른 축**이다.
- `subset`은 **문군(cluster) 단위**로 배정한다(§15.1.1 분리 규칙과 동일 원칙).
- `docs/DATA_MODEL.md` §4의 하위 호환 규칙상 **레코드 필드 추가는 허용**이다. 라벨 스키마의 지정 권위는 §7.3이 `docs/EXPERIMENT_PROTOCOL.md` §2에 위임했으므로 **규범 문서 변경 없이 가능**하다.

### ⑥ `model` → `model_id` 통일 (N7)

`summary_arch.md` §7.2 `EmbeddingResult`·§6.3 프로필 레지스트리·`configs/embedding_profiles.yaml`는 `model_id`, §8.1 `embedding_refs` 예시와 `docs/DATA_MODEL.md` §3.1만 `model`이었다. **다수 + 프로필 레지스트리(모델 식별의 원천)에 맞춰 `model_id`로 통일.** SQLite 스키마가 아직 생성되지 않아 마이그레이션 비용은 0이다.

## 결과

- 규범 문서와 파생 문서·config 사이의 모순 14건이 해소됐다.
- 전이 사유 규칙의 우선순위가 명문화돼, `apply_transition` 구현 시 해석 갈림이 없어졌다.
- 라벨 스키마가 실제 라벨러가 채울 수 있는 형태가 됐다.
- §7.5:598이 요구하던 "사유 내용"이 이제 **검증 가능한 형태**로 바뀌었다(`note` 문자열로는 강제 불가).
- `docs/ARCHITECTURE.md`는 **수정하지 않았다** — §73~75가 이미 정정 후 규범과 일치한다.

- `reason_kinds`의 인정 조건이 미결인 상태에서 Phase 5 구현에 들어갈 수 있다. **Phase 5 착수 전에 §19 #25를 해소해야 한다.**
