# ADR-0008: ConceptNode `node_type` 결정 규칙

- **상태:** 확정 (Accepted)
- **일자:** 2026-10-20
- **관련:** `summary_arch.md` §7.7, §8.10, §10.2, §19 #16·#23
- **기반:** 아키텍처 검토 M10

## 배경

§8.10 `ConceptNode`의 `node_type`은 `entity | class | attribute | attribute_value` 4값을 갖는다. 그런데 **이 값을 정하는 규칙이 문서에 없었다.**

§8.10의 v1 최소안(`literal_normalized_match`)은 **노드 동일성**만 다룬다. 표면형이 같으면 같은 노드라는 것만 정해 있고, 그 노드가 *분류*인지 *개체*인지는 정해지지 않는다.

이게 중요한 이유는 §7.7 `attribute.distinctiveness_check.v1`의 판정 기준이 **"그 속성을 가진 분류가 대상 분류 외에 존재하는가"**이기 때문이다. §10.2 대표 예시에서:

- `동물 A` — 개체 (entity)
- `개` — 분류 (class)
- `뾰족한 귀` — 속성 (attribute)

"개"가 `class`로 식별되지 않으면, "분류 외에 존재하는가"라는 판정 문장의 주어가 불명확해진다. **대표 예시가 §10.2에 의존하는데, §10.2의 판정 문장이 `node_type` 판정에 의존하는 상태**였다.

또한 §8.10의 마지막 줄 "§19 미결정: 노드 스키마의 최종 형태는 Phase 3에서 확정한다"는, Phase 3 착수 시점에 스키마가 확정되지 않은 채 구현에 들어가는 것을 허용했다.

## 검토한 대안

| 대안 | 평가 |
|---|---|
| (a) 어휘 사전으로 분류 라벨을 등록 (`configs/node_types.yaml`) | 사전이 있으면 정확하지만, 사전은 영원히 불완전하다. **단독으로는 부족** |
| (b) 표면형에서 추론 (예: "동물"이 붙으면 class) | 오류-prone. "동물 A"는 entity인데 "동물"이 들어있다. **기각** |
| (c) `node_type`을 사용하지 않는다 | §8.10의 필드가 무의미해지고, `attribute` 판별(§7.7의 "attribute/attribute_value인 노드에만 검사")이 불가능. **기각** |
| **(d) 관계 위치로 결정 + 선택적 사전** | **채택** |

## 결정

### `node_type`은 표면형이 아니라 **관계에서의 위치**로 결정한다.

| 노드가 등장한 위치 | `node_type` |
|---|---|
| `has_property`의 attribute 위치 | `attribute` |
| `has_property`의 subject 위치 | `entity` (기본값) |
| `is_a`의 object(상위 분류) 위치 | `class` |
| `is_a`의 subject 위치 | `entity` (기본값) |
| `attribute_value` 위치 | `attribute_value` |
| 그 외 / 판정 불가 | `entity` (기본값) |

- **사전 우선순위 (선택):** `configs/node_types.yaml`에 알려진 분류 어휘가 등록되어 있으면 **사전이 관계 위치 규칙보다 우선**한다. 어휘 사전이 없으면 관계 위치 규칙만 쓴다. (§19 #23: 사전 수록 범위는 선택 사항)
- **모호한 경우:** `node_type=entity` 기본값을 쓰고 `resolution_confidence`를 `low`로 기록한다. 추측을 `high`로 표시하지 않는다.
- **`attribute_value`는 v1에서 규칙으로 만들지 않는다.** `configs/attributes.yaml`의 정규화 결과는 `attribute`다.

### distinctiveness 연산은 `node_type`에 의존하지 않는다

**v1 검사 범위 = 현재 SymbolicStore에 존재하는 주어(subject) 전체.** 주어 타입(`class`/`entity`)을 가리지 않는다.

- 따라서 `node_type` 판정이 틀려도 §10.2 재현에는 영향이 없다.
- 판정 문장을 "그 속성을 가진 **다른 주어**가 존재하는가"로 읽으면 §10.2가 성립한다("개"가 다른 주어다).
- `distinctive`는 `scope`(§8.5)를 반드시 기록해야 한다(ADR-0003).

### §19 #16 해소

노드 스키마의 최종 형태를 "Phase 3에서 확정"한다는 미결정을 없애고, **v1 최소안으로 Phase 3에 들어간다.** 스키마 변경이 필요하면 ADR-0001의 개발자 경로를 따른다.

## 결과

- §10.2 대표 예시가 `node_type` 판정 불확실성에도 재현 가능하다.
- §8.10의 미결정이 제거되어 Phase 3가 스키마 확정 없이 진행되지 않는다.
- `configs/node_types.yaml`는 선택 사항이므로, 사전이 없어도 v1이 동작한다.

## 잔여 위험

- "고양이"가 `is_a`의 object 위치에 없으면(예: "고양이는 뾰족한 귀를 가질 수 있다"만 있는 경우) `node_type`이 `entity`가 된다. **§10.2 실행 전제 3에서 시드 컨텍스트 집합을 명시**하는 것으로 보완한다(§10.2 표의 전제 3).
